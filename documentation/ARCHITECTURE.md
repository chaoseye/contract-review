# Архитектура

Документ описывает устройство системы: компоненты, путь договора, анализ, протокол, интерфейс, данные и безопасность.

## 1. Обзор

```
Браузер (React, Ant Design)
   │ HTTPS (на сервере через Caddy) / HTTP на localhost
   ▼
app ─ FastAPI: REST API + раздача собранного интерфейса      ┐
worker ─ тот же код: чтение документов, анализ, очистка      ├ один Docker-образ
   │        │            └ LibreOffice, Tesseract, шрифты    ┘
   │        └ ИИ: API, совместимый с OpenAI (RouterAI, OpenRouter, Ollama…) / Codex CLI
   ▼
db ─ PostgreSQL: пользователи, настройки, проверки (временно), очередь, журнал
том data ─ временные файлы договоров, служебные файлы Codex
```

| Контейнер | Что делает | Где работает |
|---|---|---|
| `app` | API, вход, раздача интерфейса, сборка протокола при скачивании | везде |
| `worker` | задачи из очереди: чтение документа, анализ, удаление просроченных проверок | везде |
| `db` | PostgreSQL 17 | везде |
| `caddy` | HTTPS и обратный прокси | только на сервере (профиль `server`) |

`app` и `worker` собраны из одного образа и отличаются только командой запуска. Протокол собирает `app`, когда менеджер нажимает «Скачать»: это занимает секунды, и очередь для этого не нужна.

**Запуск контейнеров** (`deploy/entrypoint.sh`):
- `app`: дождаться базы (`python -m app.cli wait-db`), применить миграции (`migrate`), создать первого администратора, если пользователей нет (`bootstrap`), затем `uvicorn app.main:app`;
- `worker` стартует после того, как `app` прошёл проверку здоровья (`GET /api/health` с запросом к базе).

## 2. Как проходит проверка

```
uploaded → extracting → extracted → analyzing → ready
               │                        │
               └────────→ failed ←──────┘      (через срок жизни → удаляется целиком)
```

Если активного подключения ИИ нет, проверка останавливается на `extracted`, и в `checks.analysis` записывается причина. Анализ, поставленный в очередь, — уже `analyzing` с ходом «Ожидает анализа».

1. **Загрузка** (`backend/app/api/checks.py`).
   - `POST /api/checks` принимает файл, комментарий менеджера с параметрами сделки (до 2000 символов) и режим закупки (`procurement`: `commercial`, `223fz`, `44fz`, `unknown`).
   - Размер ограничен лимитом из раздела «Настройки» (пока его не меняли — `MAX_UPLOAD_MB`, по умолчанию 50 МБ). Большой запрос отклоняется по Content-Length ещё до разбора, точный размер проверяется при сохранении.
   - Тип определяется по содержимому (раздел 3): неподходящий файл отклоняется сразу (415), и от него ничего не остаётся.
   - Файл сохраняется как `DATA_DIR/checks/<id>/source.<тип>`, в очередь ставится задача `extract`.
2. **Чтение** (worker, `app/jobs/tasks.py`). Из файла получается список блоков с номерами пунктов (раздел 3). Пока идёт чтение, в `checks.progress` пишется, что сейчас происходит («Распознавание страницы 3 из 13»). Промежуточные файлы (`work/`) удаляются сразу после чтения, сам файл договора — как только итог чтения записан в базу; после неожиданной ошибки он остаётся для повтора. Ошибка документа даёт статус `failed` с сообщением для менеджера. После чтения, если есть активное подключение ИИ, в очередь ставится задача `analyze`, и проверка сразу получает статус `analyzing`.
3. **Анализ** (worker, `handle_analyze`):
   - наша сторона по карточке организации (раздел 4.1), сборка промпта с действующей версией промпта администратора и запрос к модели активного подключения;
   - проверка ответа: схема (с одним переспросом), цитаты, номера пунктов, ссылки (раздел 4.4);
   - результат — в `checks.result`, сведения об анализе — в `checks.analysis`, статус `ready`.

   Сверка реквизитов (раздел 4.1) не хранится: её считает `GET /api/checks/{id}` при каждом открытии проверки.
4. **Работа менеджера.** Интерфейс раз в 2 секунды спрашивает статус. Когда статус становится `ready`, менеджер видит риски и правит строки будущего протокола. Каждое действие владельца продлевает срок жизни проверки (не чаще раза в минуту), просмотр администратором — нет.
5. **Скачивание** (`app/api/protocol.py`). `GET /api/checks/<id>/protocol.docx|pdf?signature=…&stamp=…&utc_offset=…` собирает документ из протокола проверки и данных организации, отдаёт его и ничего не сохраняет. Выпуск записывается в журнал. Если правки протокола не сохраняли, документ собирается из черновика; договору без даты черновик ставит сегодняшнюю дату по часам браузера: `utc_offset` — смещение его часового пояса от UTC в минутах.
6. **Удаление** (`app/jobs/cleanup.py`).
   - Раз в 10 минут worker удаляет проверки с истёкшим сроком (из раздела «Настройки», пока его не меняли — `CHECK_TTL_HOURS`, по умолчанию 24 часа после последнего действия): строку в базе, задачи и папку с файлами.
   - Там же удаляются папки без записи в базе и незавершённые загрузки старше часа, а также файлы договоров, чтение которых кончилось сбоем: проверка уже не ждёт чтения.
   - `DELETE /api/checks/{id}` делает то же самое сразу.

## 3. Чтение документов

Модуль `backend/app/documents/`, точка входа — `extract.extract_document(путь, рабочая_папка, progress)`.

| Файл | Что делает |
|---|---|
| `detect.py` | тип по содержимому: PDF (`%PDF-`), docx (ZIP с основной частью Word, в том числе docm и шаблоны), doc (OLE с потоком `WordDocument`), RTF (`{\rtf`). Защищённый паролем docx (OLE с `EncryptedPackage`), Excel, PowerPoint, архивы и текст отклоняются. Есть защита от zip-бомб |
| `convert.py`, `process.py` | LibreOffice без интерфейса переводит .doc и .rtf (и docx в формате Strict) в .docx. У каждого запуска свой профиль (`-env:UserInstallation`) и лимит 120 секунд; по таймауту завершается вся группа процессов |
| `docx_reader.py` | разбор XML напрямую (zipfile + lxml, безопасный парсер без внешних сущностей) |
| `numbering.py` | восстановление автонумерации Word |
| `pdf_reader.py` | pdfplumber: строки текста с координатами; таблицы с линиями — отдельными ячейками. Символ исключается из текста, только если его центр внутри таблицы (иначе пропала бы строка, касающаяся рамки). Не больше 300 страниц |
| `ocr.py` | страница без текста (меньше 15 символов при наличии картинки) рендерится pypdfium2 в 300 dpi и распознаётся Tesseract (`rus+eng`, вывод TSV, один поток OpenMP на задачу, лимит 90 секунд на страницу, не больше 60 страниц). Порядок блоков Tesseract сохраняется: колонки, например реквизиты сторон, не перемешиваются. Таблицы с линиями: линии ищутся на картинке, ячейки строят функции pdfplumber, линии внутри таблиц стираются, ячейки распознаются отдельно — вырезки складываются столбиком в одну картинку (`--psm 6`), остальная страница — с забелёнными ячейками (`--psm 3`) |
| `text_lines.py` | сборка абзацев из строк PDF и скана, удаление колонтитулов |
| `segment.py` | разметка на пункты |

**Что попадает в текст docx**:
- абзацы и таблицы, в том числе вложенные, в порядке документа; элементы управления содержимым; гиперссылки; результаты полей (без кодов полей);
- надписи (text box) — сразу после абзаца, к которому привязаны;
- сноски и концевые сноски — в конце, с пометкой «[сноска N]»;
- исправления в режиме рецензирования — как принятые.

**Что не попадает:**
- колонтитулы;
- комментарии;
- скрытый текст;
- удалённые в правках фрагменты.

О скрытом тексте, правках и комментариях менеджер получает предупреждение (`checks.warnings`).

Неразрывные пробелы и табуляции заменяются обычными пробелами, повторные пробелы схлопываются. Разрывы строк внутри абзаца (например, в реквизитах) сохраняются.

**Автонумерация Word.** Номера восстанавливаются по `numbering.xml` так же, как их показывает Word:
- счётчик общий для всех `w:num`, которые ссылаются на один `abstractNum`;
- `startOverride` начинает нумерацию заново при первом абзаце этого списка;
- после абзаца уровня L уровни ниже начинаются заново, если `lvlRestart` не запрещает этого;
- `isLgl` выводит все уровни арабскими цифрами;
- поддерживаются форматы decimal, decimalZero, буквы латинские и русские, римские цифры, none и маркеры. Редкие форматы выводятся цифрами;
- нумерация бывает задана прямо в абзаце, в стиле (с наследованием через `basedOn`) или через `pStyle` уровня; `numId=0` её отключает;
- пустой нумерованный абзац тоже увеличивает счётчик, как в Word;
- пределы против испорченного файла: начальный номер — 0…32767, как в Word, номер больше этого выводится цифрами, шаблон номера — до 255 знаков, метка — до 50; уровни вне 0–8 и нечисловые значения («1e999», «nan») не учитываются. Раньше огромный `w:start` строил римские цифры и буквы миллионами символов, и чтение не кончалось.

Маркированные списки номеров не получают. В тексте блока маркер заменяется на «— ».

**PDF и сканы.** Абзац начинается, если:
- строка открывает пункт или элемент перечня;
- промежуток между строками больше обычного;
- предыдущая строка закончилась точкой, двоеточием или точкой с запятой, а эта начинается с отступа или предыдущая не дошла до края;
- строка (или предыдущая строка) похожа на заголовок;
- у скана сменился блок Tesseract.

Перенос по слогам («пред-» + «приниматель») склеивается. Номера страниц («Страница | 3», «- 3 -», «3 из 5») и строки, которые повторяются в верхней или нижней зоне на большинстве страниц, удаляются. После распознавания менеджер получает предупреждение, а при средней уверенности Tesseract ниже 70 — ещё одно.

**Разметка на пункты**. Номер пункта берётся из автонумерации или из начала текста. Блоки без номера относятся к последнему пункту, блоки до первого пункта — к преамбуле (`clause = null`). Каждый блок получает:
- метку `B0001`, `B0002`, …;
- вид: заголовок, абзац или ячейка. Заголовок — стиль Word «Heading N», уровень структуры или короткий абзац заглавными буквами. Строка, которая начинается с метки реквизита («ИНН …, КПП …», «ОГРНИП …», «ОКПО …»), — не заголовок;
- номер пункта и заголовок раздела;
- метку автонумерации, координаты ячейки таблицы и страницу (для PDF).

Так ИИ ссылается на конкретное место, а цитаты можно проверить.

**Результат** хранится в `checks.blocks` (JSON):

```json
[
  {"id": "B0042", "kind": "paragraph", "text": "9.2. В случае необоснованного нарушения ...",
   "clause": "9.2", "section": "9. ОТВЕТСТВЕННОСТЬ СТОРОН", "label": null, "table": null, "page": 4}
]
```

Посмотреть разбор файла можно командой `python -m app.cli extract <файл>`. Она выводит блоки и последовательность номеров пунктов в консоль, в логи этот текст не попадает.

## 4. Анализ

Модуль `backend/app/analysis/`.

| Файл | Что делает |
|---|---|
| `default_prompt.py` | первая версия промпта администратора: стартовый промпт и раздел позиций поставщика, который администратор заполняет сам |
| `fixed_part.py` | фиксированная часть промпта: правила системы, которые промпт администратора не меняет |
| `prompt.py` | сведения о проверке, договор по блокам, сборка запроса, переспрос |
| `schema.py` | модели ответа (pydantic) и строгая JSON Schema из них |
| `validate.py` | проверка ответа по договору: цитаты, пункты, блоки, страницы |
| `run.py` | запрос, проверка схемы с переспросом, проверка по договору |
| `evaluate.py` | оценка на паре «договор → готовый протокол разногласий» |
| `prompts.py` | версии промпта администратора: действующая версия, новая версия, активация |
| `prompt_runs.py` | прогон черновика промпта в фоне, результат только в памяти |
| `requisites.py` | наша сторона и сверка реквизитов без ИИ (раздел 4.1); `check_info` — сведения о проверке для запроса |
| `providers/`, `profiles.py` | подключения ИИ (раздел 5) |

### 4.1. Проверки без ИИ

`app/analysis/requisites.py`. Нужны данные организации: без наименования и ИНН сверка не выполняется.

- **Наша сторона.** ИНН и наименование из карточки организации ищутся в преамбуле и блоке реквизитов; для ИП — ещё «Фамилия И.О.» и «И.О. Фамилия». Роль берётся из преамбулы («именуемый в дальнейшем «Поставщик»»), иначе — из заголовка блока реквизитов («ПОСТАВЩИК:»). Если роль не «поставщик» или нас не нашли, появляется предупреждение.
- **Реквизиты.** Опора — последний блок с нашим ИНН после преамбулы, а если ИНН нет — последний блок с наименованием во второй половине договора. Блок реквизитов — от нашего заголовка или ИНН до заголовка другой стороны, чужого ИНН или следующего раздела:
  - реквизиты абзацами — соседние блоки, не больше 8 назад и 16 вперёд;
  - реквизиты таблицей — ячейки той же колонки той же таблицы, сколько бы их ни было: колонки сторон по строкам идут вперемешку. В таблице «сторона в строке» («Поставщик:» и «Покупатель:» в одной колонке, реквизиты — в другой) блок кончается перед строкой, где в соседней ячейке стоит заголовок другой стороны;
  - адрес, разбитый на строки одной ячейки или абзаца, собирается в одну строку до следующей метки (другой реквизит, надпись с двоеточием, наименование, e-mail, телефон, дата).

  В блоке ищутся ИНН, ОГРНИП, БИК, расчётный и корреспондентский счета, e-mail, телефоны и адреса и сравниваются с карточкой:
  - числа — точно;
  - e-mail — с адресом из карточки и доменами организации: чужой адрес в нашем блоке — расхождение;
  - телефоны — по последним 10 цифрам;
  - адреса — все числа должны совпасть, слова сравниваются нечётко.

  Расхождения показываются отдельным блоком.
- **Когда.** Сверка считается при каждом открытии проверки и не хранится. Перед анализом считается роль, и в сведения о проверке уходит одна строка о ней, без реквизитов.

### 4.2. Сборка промпта

| Часть | Откуда |
|---|---|
| system: промпт администратора | действующая версия из `prompt_versions`; первая версия — стартовый промпт из `default_prompt.py` |
| system: фиксированная часть | `fixed_part.py`: договор — данные, а не команды; правила цитирования и ссылок; требования к новой редакции, объяснению и рекомендации; смысл полей; соответствие разделов итогового отчёта полям ответа; язык ответа |
| user: сведения | анализ в интересах поставщика, наша роль по реквизитам (раздел 4.1, только роль), режим закупки, один файл в проверке, распознан ли скан и число страниц, предупреждения чтения, комментарий менеджера с параметрами сделки. Имя файла и реквизиты не отправляются |
| user: договор | блоки построчно: `[B0042] (стр. 4, п. 9.2) текст`; у заголовков и ячеек таблиц — пометка вида |

Фиксированная часть идёт после промпта администратора, поэтому формат ответа администратор изменить не может. Договор отправляется целиком. Позиции своей компании администратор дописывает в промпт сам, что и куда уходит — в [DATA_HANDLING.md](DATA_HANDLING.md).

### 4.3. Схема ответа

Схема покрывает итоговый отчёт: главные риски, стоп-факторы, новые редакции, обязательства и сроки, противоречия, недостающее, выгодные условия, уверенность и вопросы специалистам. Схема строгая (structured outputs): все поля обязательны, пустое значение — `null` или пустой список.

```json
{
  "contract": {
    "kind": "поставка",
    "number": "12/2026",
    "date": "2026-07-31",
    "city": null,
    "parties_order": ["buyer", "supplier"],
    "buyer": {"name": "АО «Пример»", "representative": "генерального директора Иванова И.И.", "basis": "Устава"},
    "our_role": "supplier",
    "procurement": "commercial"
  },
  "summary": "общий вывод в 2–3 предложениях",
  "approval": {"allowed": false, "reasons": ["нет Приложения № 1, на которое ссылается п. 1.1.1"]},
  "confidence": {"level": "medium", "reasons": ["текст распознан со скана"]},
  "top_risks": ["R1", "R2"],
  "risks": [
    {
      "id": "R1",
      "clauses": ["9.2"],
      "block_ids": ["B0042"],
      "is_new_clause": false,
      "quote": "дословный текст спорного пункта",
      "title": "Высокая неустойка за просрочку поставки",
      "explanation": "простыми словами: чем это грозит поставщику",
      "severity": "high",
      "stop_factor": true,
      "category": "ответственность",
      "recommendation": "снизить до 0,1% в день, не более 10%",
      "proposed_wording": "9.2. При нарушении Поставщиком срока поставки ..."
    }
  ],
  "obligations": [
    {"party": "buyer", "obligation": "оплатить остаток", "deadline": "7 рабочих дней с подписания УПД",
     "clauses": ["2.2"], "block_ids": ["B0012"]}
  ],
  "contradictions": [{"description": "срок приёмки в п. 6.1 и в спецификации разный", "clauses": ["6.1"], "block_ids": ["B0051"]}],
  "missing": [{"item": "Приложение № 1 — технический паспорт", "reason": "на него ссылается п. 1.1.1"}],
  "favorable": [{"description": "оплата считается с зачисления на счёт поставщика", "clauses": ["2.4"],
                 "block_ids": ["B0013"], "quote": "..."}],
  "specialist_checks": [{"specialist": "lawyer", "what": "полномочия подписанта по доверенности"}]
}
```

- `severity` — `high`, `medium` или `low`; `stop_factor` — с этим условием договор нельзя подписывать без исправления.
- У нового пункта `is_new_clause = true`, `quote` пустой, а в `clauses` стоит предлагаемый номер.
- `top_risks` — до пяти идентификаторов из `risks`.
- `procurement` — режим закупки по тексту договора: `commercial`, `223fz`, `44fz` или `unknown`. Если он не совпадает с тем, что указал менеджер, это противоречие.
- `specialist` — `lawyer`, `finance`, `production` или `security`.
- `party` — `buyer` или `supplier`.

### 4.4. Проверка ответа

1. **Схема.** Ответ проверяется моделями pydantic — теми же, из которых построена схема. Если ответ не JSON или не проходит схему, запрос повторяется один раз, к нему прикладывается перечень ошибок (где и что не так, без значений из ответа). При второй ошибке проверка получает статус `failed` с понятным сообщением. Дата вида «31.07.2026» приводится к ГГГГ-ММ-ДД без переспроса.
2. **Цитаты**.
   - Сначала текст нормализуется: неразрывные пробелы, кавычки «»“”", тире, ё/е, регистр, пробелы перед знаками препинания и «%».
   - Затем цитата ищется в блоках из `block_ids`, потом во всём договоре (в том числе на стыке блоков): сначала точно, потом нечётко (`rapidfuzz.partial_ratio ≥ 90`, для цитат от 12 символов).
   - Результат сохраняется в `quote_status`: `exact`, `fuzzy`, `not_found`, `empty` (цитаты нет) или `new_clause`. Блоки, где цитата нашлась, и их страницы записываются рядом; ссылка на не тот блок так исправляется.
3. **Номера пунктов.** Каждый номер в `clauses` должен быть в разметке. Если номера нет и это не новый пункт, риск помечается. «п.», «пп.», «пункт» перед номером не учитываются (`normalize_clause`). Ссылка на приложение («Приложение № 1», «Спецификация», «п. 3 Приложения № 1») сводится к одному виду и сверяется не с номерами пунктов, а с началами приложений:
   - приложение есть в договоре, если с его названия начинается заголовок или строка, где после названия ничего нет или идёт «к договору …»: «Приложение 1», «Приложение № 1 к контракту …», «СПЕЦИФИКАЦИЯ»;
   - упоминание в тексте пункта («указаны в Приложении № 2») не считается; строка перечня «Приложение № 1 – Спецификация.» только связывает два названия одного приложения;
   - «Спецификация» и «Приложение» без номера — любая спецификация или любое приложение из файла;
   - номер пункта внутри приложения не сверяется: у спецификации-таблицы номеров нет, а своя нумерация приложения в разметке смешана с номерами договора.
4. **Ссылки в остальных разделах.** Метки блоков и номера пунктов проверяются и в `obligations`, `contradictions`, `favorable`; в `top_risks` допускаются только идентификаторы из `risks`. Страница для каждого блока берётся из разметки.

### 4.5. Стоимость

По прайсу RouterAI на 2026-10-16 Claude Sonnet 5.5 стоит 217,78 ₽ за 1 млн входных токенов и 1088,88 ₽ за 1 млн выходных, но серверы у него только в США. Анализ договора на 20 страниц обходится примерно в 10–20 ₽. На серверах в РФ: GigaChat 3 Pro — 87,64 ₽ и 211,67 ₽, DeepSeek V4 Flash у провайдера Yandex — 390 ₽ и 650 ₽. ## 5. Подключение ИИ

Модуль `backend/app/analysis/providers/`, профили подключений — `app/analysis/profiles.py`, команды — `app/analysis/cli_commands.py`.

**Общий интерфейс** (`base.py`). Подключение получает `AnalysisRequest`: system, user и JSON Schema ответа. Возвращает `AnalysisResult`:
- разобранный JSON-объект;
- токены и стоимость в рублях — точную или оценку по ценам;
- модель, способ получения JSON и длительность.

Проверку ответа по схеме, цитат и номеров пунктов делает анализ (раздел 4.4). Метод `check()` проверяет связь коротким запросом без договора.

**Ошибки:**

| Класс | Когда | Повтор |
|---|---|---|
| `ProviderConfigError` | ключ не принят (401), нет денег (402), нет доступа (403), нет модели или провайдеров в РФ (404), запрос отклонён (400), нет входа в Codex | нет |
| `ProviderUnavailableError` | нет сети, таймаут, 429, 5xx, перегрузка Anthropic (529 или ошибка в потоке) | да; кроме исчерпанного лимита подписки Codex |
| `ProviderResponseError` | ответ не JSON, обрезан по длине, модель отказалась, договор не помещается в контекст | анализ переспрашивает один раз (раздел 4.4) |

У ошибки есть текст для людей и отдельно ответ провайдера (`detail`) для администратора. В лог не пишется ни то, ни другое, только тип ошибки.

| Тип | Как работает |
|---|---|
| `openai_compat` (`openai_compat.py`) | SDK `openai` 3.24 с настраиваемым `base_url`. **Формат ответа** в режиме `auto`: structured outputs (`json_schema`, `strict`), если модель их поддерживает; иначе JSON-режим со схемой в инструкции; иначе только инструкция. Если провайдер отклоняет `response_format` (400), берётся следующий вариант. **«Только серверы в РФ»** (только RouterAI) добавляет `provider.country = "ru"`. **Модели и цены** — `GET /models` (RouterAI — рубли за токен). При «Только серверы в РФ» цена берётся у провайдера с серверами в РФ из `GET /models/{модель}/endpoints`. **Стоимость** — из `usage.cost`, если провайдер её вернул, иначе по ценам. **Повторы** при сетевых ошибках, 429 и 5xx делает SDK. **OpenAI напрямую** (`api.openai.com`): лимит длины уходит как `max_completion_tokens`, в списке моделей — только модели для Chat Completions |
| `anthropic` (`anthropic_api.py`) | SDK `anthropic` 1.11, Messages API, ответ потоком; лимит времени — на весь ответ. **Формат ответа** в режиме `auto`: строгая схема (`output_config.format`), если модель её поддерживает, иначе инструкция; JSON-режима нет. **Возможности модели** (схема, `effort`, adaptive thinking, контекст, предел ответа) — из `GET /v1/models/{модель}` при проверке связи. **Глубина рассуждений** — `output_config.effort` из подключения. **Длина ответа** — `max_output_tokens` или 64 000 (не больше предела модели). **Кэш промпта** — `cache_control` на промпте системы. **Резервная модель** при отказе классификатора — `fallbacks: "default"` для Claude Fable 5.1, Opus 5.5, Opus 5 и Sonnet 5.5, только на `api.anthropic.com`. **Стоимости нет**: цен в API нет. **Повторы** при сетевых ошибках, 429, 5xx и 529 делает SDK |
| `codex_cli` (`codex_cli.py`) | `codex exec --json --color never --sandbox read-only --skip-git-repo-check --ephemeral --ignore-user-config --ignore-rules --cd <пустая папка> --output-schema <файл> -o <файл> [--model …] -` в новой временной папке, задание через stdin. Токены — из события `turn.completed`, стоимости нет (подписка). Окружение процесса — только `PATH`, `HOME`, язык, прокси, сертификаты и `CODEX_HOME`, без секретов приложения. Вход: `codex login --device-auth` — система показывает ссылку и код, администратор входит в свой аккаунт ChatGPT; вход хранится в `DATA_DIR/codex`. Для работы — когда системой пользуется один менеджер и сервер стоит не в России, иначе только для разработки и тестов. В образе Codex есть, только если он собран с `INSTALL_CODEX=true` |

**Параметры подключения** (`llm_profiles.params`, модель `ProfileParams`):

| Параметр | По умолчанию | Что делает |
|---|---|---|

**Админка.** Раздел «Подключения ИИ» добавляет, меняет, удаляет подключения, выбирает действующее, проверяет связь и показывает модели с ценами. Там же — вход в Codex по коду устройства. **Ключ и адрес.** Сохранённый ключ отправляется только на тот сервер, для которого его ввели: схема, имя и порт адреса API (`profiles.same_server`). Новый адрес на другом сервере без нового ключа не сохраняется, «Список моделей» с таким адресом не подставляет сохранённый ключ, а загрузка настроек сбрасывает ключ и просит ввести его заново.

## 6. Протокол

Модуль `backend/app/protocol/`. Точное описание документа — в [PROTOCOL_FORMAT.md](PROTOCOL_FORMAT.md).

| Файл | Что делает |
|---|---|
| `model.py` | `ProtocolData` — всё, что попадает в документ: шапка, строки, заключительные положения, стороны, бланк, размер шрифта таблицы. `ProtocolImages` — шапка бланка, подпись и печать байтами |
| `templates.py` | тексты по умолчанию и подстановки: дата прописью, подписи пунктов, «именуемое / именуемый», вступление, заключительные положения, неразрывные пробелы; `build_protocol_data` собирает `ProtocolData` из данных договора |
| `assets.py` | подготовка картинок через Pillow: прозрачный белый фон у скана без прозрачности, поворот из EXIF, обрезка пустых краёв, поворот печати на постоянный для договора угол, прозрачность; `covers_text` — фон и после этого закроет текст |
| `builder_docx.py` | `build_docx(data, images, with_signature, with_stamp)` → байты docx. python-docx и прямая правка XML там, где python-docx не умеет: повтор шапки, фиксированный макет таблицы, поле `PAGE`, плавающие картинки |
| `pdf.py` | `docx_to_pdf` — PDF через LibreOffice, тот же вызов, что при чтении .doc (`documents/convert.py`) |

Генератор ничего не вычисляет сам и не обращается к базе: данные собирает протокол проверки (раздел 6.1). Для ручной проверки протокол собирается командой `python -m app.cli protocol <данные.json>`.

### 6.1. Данные протокола

Они хранятся в проверке, в поле `checks.protocol` (`ProtocolState` в `app/protocol/editing.py`), и меняются менеджером:
- `meta`: заголовок, вид, номер и дата договора, город, дата протокола, покупатель (полное и короткое наименование, представитель, основание, расшифровка подписи), порядок сторон, колонка «Согласованная редакция», приложения, своё вступление, размер шрифта таблицы;
- `rows`: строки таблицы по порядку. У строки есть ссылка на риск (у своих строк менеджера её нет), признак «в протокол», подпись пункта («п. 9.2», «пп. 6.1, 6.3 и 6.5», «п. 9.9 (новый пункт)»), редакция покупателя и редакция поставщика.

Пока менеджер ничего не сохранил, протокол — черновик из результата анализа и шаблона протокола (заголовок, колонка «Согласованная редакция», шрифт таблицы): колонка покупателя — полный текст пункта из договора, колонка поставщика — новая редакция, по умолчанию в протокол входят риски с редакцией, кроме низкой критичности. Значения из ответа модели, которые длиннее полей протокола (номер договора — 100 знаков, редакции — 20 000, строк — 300), обрезаются и кончаются «…». Строка с обрезанной редакцией в протокол по умолчанию не входит: менеджер сначала её проверяет. Ссылка на риск не обрезается: если id риска длиннее 200 знаков, строка остаётся без ссылки, как свой пункт. Данные поставщика (наименование, подписант, подпись и печать) берутся из таблицы `organizations`. Обязательно только полное наименование: без краткого в блоке подписей стоит полное, без подписанта — линия.

### 6.2. Документ

- **Страница.** A4 альбомный, поля — в [PROTOCOL_FORMAT.md](PROTOCOL_FORMAT.md#1-страница).
- **Верхний колонтитул.** По умолчанию пуст. Если бланк включить в шаблоне, шапка ставится только на первой странице (`titlePg`).
- **Нижний колонтитул.** «Страница N» через поле `PAGE`. Поле сложное (`fldChar`), размер 9 pt задан у каждой его части: простое поле Word при обновлении набирает размером стиля Normal. Контакты (8 pt, серым, шрифтом текста) — только если включён бланк.
- **Начало.** Заголовок и строка «к Договору … № … от …» по центру. Город слева, дата справа. Затем вступление по шаблону, стороны в порядке договора.
- **Таблица.** У строки заголовка стоит `tblHeader`, поэтому она повторяется на каждой странице. Заливка заголовка светлая. Строкам разрешено переноситься на следующую страницу. Макет таблицы фиксированный, чтобы ширины колонок в Word и PDF совпадали. Колонку «Согласованная редакция» можно отключить. Шрифт таблицы — 10 pt.
- **Конец.** Заключительные положения по шаблону, затем таблица подписей в две колонки: ПОКУПАТЕЛЬ слева, ПОСТАВЩИК справа, у каждой стороны строка «______ / И.О. Фамилия /» и «М.П.».
- **Подпись.** PNG вставляется как плавающий объект (`wp:anchor`) над линией подписи, шириной 34 мм. У скана подписи и печати без прозрачности белый фон перед вставкой становится прозрачным.
- **Печать.** PNG диаметром 40 мм ставится на «М.П.» и немного заходит на подпись. Положение обеих картинок задано от верха абзаца, а строки блока подписей — точной высоты, поэтому Word и LibreOffice ставят их одинаково. Перед вставкой картинка поворачивается на 2–6° и получает прозрачность около 85%, чтобы текст под ней читался.
- **Шрифты.** Весь документ набран Times New Roman: 10 pt в таблице, 11 pt в остальном тексте. Тематические шрифты Word в стилях сброшены, иначе Word подставил бы шрифт темы.
- **Тексты.** Заголовок, вступление, заключительные положения и пункт о приложениях собираются по шаблону протокола с подстановками из списка ([PROTOCOL_FORMAT.md](PROTOCOL_FORMAT.md#7-тексты-и-подстановки)). Шаблон правится в админке и хранится в `settings`; тексты по умолчанию — в `templates.py` (`ProtocolTemplate`).

### 6.3. PDF

LibreOffice без интерфейса переводит собранный docx в PDF, поэтому оба файла выглядят одинаково. На машине разработчика вид docx дополнительно проверяется в Word.

**Шрифты в образе**:
- Liberation Serif метрически совпадает с Times New Roman, поэтому строки и страницы в PDF ложатся так же. Настоящий Times New Roman требует принять лицензию Microsoft.
- Jost не нужен: контакты набираются шрифтом текста.
- В Word у получателя документ открывается с Times New Roman.

| Мои проверки (`ChecksPage`, `pages/checks.css`) | зона «Перетащите договор сюда»; проверки: вид и номер договора и покупатель (или имя файла), ход тремя полосками с подписью — до скачанного протокола, время до удаления, «Запустить анализ» или «Открыть», удаление в меню «⋯»; список обновляется, пока что-то обрабатывается |

| Проверка (`CheckPage`, `components/check/`, стили — `check.css`) | путь «Анализ → Риски → Протокол», полоса шагов — `CheckSteps`, шаг в адресе: `?step=protocol`. Над шагами — наша сторона и сверка реквизитов (`RequisitesCard`: всё совпало — строка, расхождения — карточка), предупреждения чтения (OCR и др.), меню «⋯»: анализ заново, удалить проверку. **Анализ** (`AnalysisStep`) — чтение и анализ с ходом и временем; «Запустить анализ», если он не запущен или не выполнен. **Риски** (`RisksStep`, `RiskCard`) — вывод («подписывать без правок нельзя» с причинами, уверенность), фильтр (все, главные, стоп-факторы, по критичности), риски по важности рядом с текстом договора (`ContractText`: пункт риска подсвечен, остальные риски — светлым маркером, номера страниц у PDF); в карточке — объяснение, чего добиться, текст договора и наша редакция, «В протокол / Не включать»; «Справка по договору» — обязательства, противоречия и недостающее, выгодные условия, вопросы специалистам в шторке (`ReferenceDrawer`, `SectionsTabs`). **Протокол** (`ProtocolStep`) — документ, как его увидит покупатель: выбор строки, правка в окне, порядок, убрать и вернуть, свой пункт; данные протокола, оформление, подписи и вступление; «Подпись» и «Печать», «Скачать Word», «Скачать PDF», «Сбросить правки». Правки сохраняются сами (`useProtocol`, через 0,8 с после ввода). Модель, токены и стоимость — только администратору, в «Подробностях анализа» |

### 7.2. Администратор

Администратор видит всё, что видит менеджер, плюс раздел «Администрирование» (`/admin`, `frontend/src/pages/admin/`, отдельные модули, которые загружаются только при открытии). Права проверяет сервер, интерфейс только прячет раздел от менеджера (`RequireAdmin`). Меню (`AdminLayout`): «Обзор», затем группы «Чтобы анализ работал» (подключения ИИ, организация, пользователи) и «Тонкая настройка» (промпт, шаблон протокола, настройки и перенос, журнал). Готовность считает `readiness.ts` по организации, подключениям, входу в Codex и пользователям; разделы обновляют её после своих изменений, и точка у раздела в меню пропадает сразу.

| Раздел | Что в нём |
|---|---|
| Обзор | готово ли то, без чего менеджер не проверит договор и не выпустит протокол: действующее подключение ИИ (у Codex — и вход), полное наименование организации, подпись и печать, активные менеджеры; каждый пункт ведёт в свой раздел |
| Пользователи | создание со случайным паролем, имя и роль, блокировка, новый пароль |
| Промпт | редактор действующей версии, сохранение и черновик, версии (автор, дата, комментарий), построчное сравнение, откат, прогон черновика на договоре без сохранения |
| Подключения ИИ | все подключения: действующее, проверка связи, правка, в меню «⋯» — сделать действующим и удалить; модели с ценами (и до сохранения подключения), «Только серверы в РФ» — только у адреса RouterAI. Codex по подписке ChatGPT — четыре шага: подготовить аккаунт, войти по коду, создать подключение (форма заполнена) или сделать его действующим, проверить связь; метка, идёт ли анализ и через что. Шаги — над списком, когда анализ идёт или должен пойти через Codex, иначе под ним; без Codex на сервере — короткая карточка, что он недоступен |
| Организация | наименования, подписант, город, контакты для колонтитула, реквизиты для сверки с проверкой формата, домены e-mail организации — сохраняются кнопкой «Сохранить данные и реквизиты»; подпись, печать и шапка — сразу при загрузке, с предпросмотром «как в протоколе» и предупреждением, если фон подписи или печати закроет текст |
| Шаблон протокола | заголовок, вступление, заключительные положения, пункт о приложениях с подсказками подстановок, колонка, бланк, шрифт; предпросмотр текста и образец Word и PDF |
| Настройки и перенос | срок жизни проверки и лимит файла, выгрузка и загрузка настроек одним файлом |
| Журнал | действия и расходы, фильтры по дате, пользователю, действию и проверке, итоги, CSV |

## 10. Фоновые задачи

Код: `app/jobs/queue.py`, `tasks.py`, `worker.py`, `cleanup.py`.

- **Очередь** — таблица `jobs`. Worker забирает задачи через `SELECT … FOR UPDATE SKIP LOCKED` в `WORKER_CONCURRENCY` потоков (по умолчанию 2). Свободный поток проверяет очередь раз в секунду. На SQLite (разработка) поток один: там нет `SKIP LOCKED`.
- **Длинная работа вне транзакции.** Короткая сессия перед задачей и после неё; чтение и распознавание идут без открытой транзакции.
- **Признаки жизни.** Пока задача выполняется, worker обновляет `locked_at` (при распознавании — на каждой странице). Задача без обновлений дольше 5 минут считается зависшей и возвращается в очередь. Проверка зависших — раз в минуту.
- **Повторы.** Ошибка документа (`DocumentError`) не повторяется: проверка получает `failed` с сообщением для менеджера. Неожиданное исключение при чтении повторяется через 30 секунд, после второй неудачи проверка получает `failed` с общим сообщением о внутренней ошибке. Неожиданное исключение при анализе не повторяется (`tasks.RETRY_UNEXPECTED`): оно могло случиться после ответа модели, а повтор снова отправил бы договор платной модели. Сообщение — «Анализ не выполнен из-за внутренней ошибки…», файл загружать заново не нужно. Временные ошибки ИИ сначала повторяет SDK внутри запроса; задача `analyze` повторяется ещё до 3 раз (`queue.RetryLater`: 30 секунд, 2 и 10 минут), пока ждёт — менеджер видит причину. Ошибки настроек и негодный ответ не повторяются.
- **Задача и её ошибка** меняют проверку, только пока та ждёт этой задачи (`queue.waits_for`): чтение — в `uploaded` и `extracting`, анализ — в `analyzing`. Повтор задачи, которая уже выполнилась, но не успела отметить это в очереди, ничего не делает. Итог задачи записывается под блокировкой строки проверки и только пока проверка его ждёт: поздний итог второго выполнения той же задачи отбрасывается. Любая неудача анализа пишется в журнал («анализ не выполнен»: модель и сообщение).
- **Лимиты времени.** LibreOffice — 120 секунд, Tesseract — 90 секунд на страницу, запрос к ИИ задаётся в подключении (по умолчанию 300 секунд). Ответ модели может идти дольше 5 минут, поэтому, пока задача `analyze` ждёт ответа, отдельный поток раз в 30 секунд обновляет `locked_at` (`queue.keep_alive`): иначе её сочли бы зависшей.
- **Очистка** раз в 10 минут: просроченные сессии, просроченные проверки вместе с файлами, файлы договоров у проверок, которые уже не ждут чтения (остаток после сбоя), папки без записи в базе, незавершённые загрузки и временные папки заданий Codex (`DATA_DIR/tmp`) старше часа.
- **Логи** содержат тип исключения и стек вызовов, но не текст сообщения.
- **Поток задач** не останавливается, если не удалось записать итог задачи (например, база недоступна): ошибка — в лог, задача вернётся в очередь как зависшая.
- **Остановка.** По SIGTERM worker дожидается текущих задач до 30 секунд.

## 11. Безопасность

- **Вход.** Пароли хранятся в виде хешей Argon2. Если логин не найден, всё равно выполняется проверка фиктивного хеша, чтобы по времени ответа нельзя было понять, существует ли логин.
- **Сессии.** Сессия хранится в cookie `contract_review_session` с флагами `HttpOnly` и `SameSite=Lax`; при `PUBLIC_URL` на https добавляется `Secure`. В базе лежит только HMAC токена. Срок продлевается при активности.
- **CSRF.** Изменяющие запросы к `/api/` принимаются только с заголовком `X-Requested-With: contract-review`.
- **Подбор пароля.** После 5 неудачных попыток за 15 минут по логину или 20 с одного адреса вход отклоняется (429). За Caddy адрес клиента берётся из `X-Forwarded-For`, только если запрос пришёл с адреса из `FORWARDED_ALLOW_IPS`.
- **Заголовки.** На всех ответах — `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: same-origin` и `Permissions-Policy` без камеры, микрофона и геолокации; заголовка `Server` нет. На страницах и файлах интерфейса — `Content-Security-Policy`: скрипты только свои, встраивать страницы нельзя. На ответах API — `Cache-Control: no-store`. HSTS ставит Caddy (профиль `server`).
- **Размер запросов.** Загрузка договора ограничена настройкой из админки, остальные изменяющие запросы к API — 48 МБ; оба предела проверяются по Content-Length до разбора запроса.
- **Права** проверяются на сервере в каждом обработчике. Менеджер получает только свои проверки, `/api/admin/*` доступен только администратору.
- **Ключи ИИ** шифруются ключом `ENCRYPTION_KEY` из `.env` (Fernet). В командной строке и интерфейсе видны только последние 4 символа. Ключ не передаётся аргументом команды и не уходит на сервер, для которого его не вводили (раздел 5).
- **Схема API.** `/api/docs` и `/api/openapi.json` есть только при `API_DOCS=true` — для разработки.
- **Данные договоров** не попадают в логи: там только идентификаторы. В резервные копии и выгрузку настроек тексты не входят. Файл договора удаляется сразу после чтения.
- **Шифрование на сервере.** Резервные копии шифруются открытым ключом age. На арендованном сервере данные Docker, код с `.env` и копии можно держать на диске LUKS (`deploy/server/contract-review-disk.sh`), ключ — у владельца. На незашифрованной части swap, kdump и дампы памяти выключены, swap есть только внутри зашифрованного диска. От подмены программ выключенного сервера диск не защищает.
- **Файрвол на сервере.** ufw пропускает только 22, 80 и 443. Порты, которые публикует Docker, идут мимо него: приложение закрыто `APP_BIND=127.0.0.1`, у базы портов нет.
- **Агент хостера.** qemu-guest-agent на арендованном сервере ограничен: не выполняет команды, не читает и не пишет файлы, не меняет пароли и ключи SSH. Пароль root — свой, хранится у владельца.
- **Загрузка файлов.** Тип проверяется по содержимому, а не по расширению: программа, HTML или чужой архив под видом договора отклоняются сразу (415). Размер ограничен. Защита от zip-бомб — не больше 5000 частей и 300 МБ в распакованном виде, одна XML-часть — не больше 64 МБ. Повреждённые docx и PDF дают понятное «Файл повреждён». В PDF — не больше 300 страниц, распознаётся не больше 60, страница при распознавании — не больше 5000 точек по стороне. XML читается без внешних сущностей (XXE). Файлы лежат в отдельной папке проверки. LibreOffice и Tesseract запускаются отдельными процессами с лимитом времени.
- **Попытки управлять ИИ** текстом договора. Фиксированная часть промпта велит считать договор данными, ненайденные цитаты помечаются, а итог всё равно проверяет менеджер.
- **Codex CLI** запускается с песочницей только на чтение, в пустой папке, без сохранения сессий и без секретов приложения в окружении. В контейнере сама песочница не запускается, и команды агента не выполняются: контейнеру не дают прав, которые ей нужны.
- **Логи HTTP-клиента и SDK `openai`** ограничены уровнем WARNING даже при `LOG_LEVEL=DEBUG`.

## 12. Конфигурация

Настройки машины лежат в `.env` (образец — `.env.example`). Файл со случайными секретами создаёт `python deploy/scripts/init_env.py`. Всё остальное хранится в базе. Приложение читает переменные окружения и `.env` в корне репозитория; переменные окружения важнее (`backend/app/core/config.py`).

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `PUBLIC_URL` | адрес, по которому открывают систему; `https://` включает флаг `Secure` у cookie | `http://localhost:8080` |
| `APP_BIND`, `APP_PORT` | интерфейс и порт хоста (только compose) | `127.0.0.1`, `8080` |
| `POSTGRES_PASSWORD` | пароль базы; из него compose собирает `DATABASE_URL` | — (обязательно) |
| `DATABASE_URL` | адрес базы; compose задаёт `postgresql+pg8000://contract_review:…@db:5432/contract_review` | без Docker — SQLite `backend/data/dev.db` |
| `APP_SECRET_KEY` | ключ HMAC для токенов сессий, от 32 символов, заглушка `change-me` не принимается | — (обязательно) |
| `ENCRYPTION_KEY` | ключ Fernet для ключей подключений ИИ; без него ключ API не сохранить | пусто (`init_env.py` создаёт) |
| `CODEX_BIN` | команда или путь к Codex CLI; нужен только без Docker, если `codex` не в `PATH` | `codex` |
| `INITIAL_ADMIN_LOGIN`, `INITIAL_ADMIN_PASSWORD` | первый администратор, создаётся, только если пользователей нет; пароль от 8 символов | `admin`, пусто |
| `SESSION_TTL_HOURS` | срок сессии без активности, часов | `12` |
| `CHECK_TTL_HOURS` | срок жизни проверки после последнего действия, часов — пока администратор не задал свой в разделе «Настройки» | `24` |
| `MAX_UPLOAD_MB` | максимальный размер договора — так же, до настройки в админке | `50` |
| `WORKER_CONCURRENCY` | число одновременных задач worker | `2` |
| `LOG_LEVEL` | подробность логов | `INFO` |
| `API_DOCS` | `true` — схема API и Swagger на `/api/docs`, только для разработки | `false` |
| `SITE_ADDRESS` | домен для Caddy (профиль `server`) | `localhost` |
| `COMPOSE_PROFILES` | `server` — включить Caddy для всех команд `docker compose` | пусто |
| `BACKUP_AGE_RECIPIENT` | открытый ключ age (`age1…`), которым `backup.py` шифрует копии; читают только скрипты копий, не приложение | пусто — копии не шифруются |
| `FORWARDED_ALLOW_IPS` | адреса обратного прокси, которому приложение верит в `X-Forwarded-For`; за Caddy — `*` при `APP_BIND=127.0.0.1` ([DEPLOYMENT.md](DEPLOYMENT.md#33-сервер-с-доменом-и-https)) | `127.0.0.1` |
| `DATA_DIR`, `STATIC_DIR` | папка временных файлов и собранного интерфейса; заданы в образе | `/data`, `/app/static` |

Только для тестов: `TEST_POSTGRES_URL` — отдельная база `*_test` для проверки очереди на PostgreSQL.

Параметры сборки образа: `INSTALL_DEV=true` добавляет pytest, ruff и reportlab, чтобы запускать тесты в контейнере. `INSTALL_CODEX=true` добавляет Codex CLI (версия — `CODEX_VERSION`, по умолчанию 0.160.0). `INSTALL_CODEX` берётся из `.env` через `docker-compose.yml`, поэтому Codex остаётся в образе и после обновлений.

## 13. Развёртывание

| Где | Как |
|---|---|
| Компьютер разработчика | Docker Desktop: `python deploy/scripts/init_env.py`, затем `docker compose up -d --build`, http://localhost:8080. Без Docker: `backend/run_dev.py` на SQLite и `npm run dev` |
| Сервер с доменом | тот же compose: `docker compose --profile server up -d --build`. Caddy получает сертификат Let's Encrypt для `SITE_ADDRESS`; порт приложения остаётся на 127.0.0.1 |
| Арендованный сервер (VPS) | то же, но данные Docker, код и `.env` — на зашифрованном диске LUKS: `deploy/server/contract-review-disk.sh`, после перезагрузки владелец открывает диск своим ключом; файрвол ufw — только 22, 80 и 443; агент хостера ограничен; сигналы о работе сервера и ночной копии — в Healthchecks.io, `deploy/server/contract-review-monitor.sh` |
| Сервер в локальной сети | тот же compose: Caddy с внутренним сертификатом или `APP_BIND=0.0.0.0` и HTTP. Без интернета нужен локальный ИИ: Ollama или vLLM через `openai_compat` |

Данные лежат в томах Docker: `pgdata` (база), `appdata` (временные файлы проверок), `caddy_data` и `caddy_config` (сертификаты). `docker compose down` тома не удаляет.

**Резервные копии и перенос**:
- `python deploy/scripts/backup.py` — дамп PostgreSQL в `backups/`: пользователи, настройки, организация с картинками, журнал. Данных проверок и сессий в нём нет. С `BACKUP_AGE_RECIPIENT` дамп из памяти шифруется age, на диск пишется только `.dump.age`.
- `python deploy/scripts/restore.py <копия>` — сначала копия текущей базы, затем очистка схемы, загрузка копии и запуск; миграции доводят старую копию до текущей версии. Зашифрованная копия расшифровывается в памяти ключом владельца (`--identity`) ещё до остановки системы.
- Перенос на другую машину — это восстановление копии на новой установке с тем же `.env`. Проверки не переносятся, потому что они временные.

Установка, варианты размещения, обновление, расписание копий и проверки перед запуском — в [DEPLOYMENT.md](DEPLOYMENT.md).
