# Развёртывание и эксплуатация

Документ для того, кто ставит систему на сервер или переносит её на другую машину: установка, варианты размещения, обновление, резервные копии, восстановление, диагностика и проверки безопасности. Как устроена система, описано в [ARCHITECTURE.md](ARCHITECTURE.md), куда уходят данные договоров — в [DATA_HANDLING.md](DATA_HANDLING.md).

## 1. Что нужно

| Что | Зачем |
|---|---|
| Docker Engine 24 или новее с плагином compose (Linux) либо Docker Desktop (Windows, macOS) | система работает в контейнерах: `app`, `worker`, `db`, для HTTPS — `caddy` |
| Python 3.10 или новее | скрипты в `deploy/scripts/`: создание `.env`, резервные копии. Нужна только стандартная библиотека |
| age | шифрование резервных копий (раздел 5): `apt install age`, в Windows — `winget install FiloSottile.age` |
| cryptsetup (Linux) | зашифрованный диск на арендованном сервере (раздел 11): `apt install cryptsetup` |
| Git | получить и обновлять код |
| Сервер: минимум 2 vCPU, 4 ГБ памяти, 40 ГБ SSD; лучше 4 vCPU, 8 ГБ, 80 ГБ NVMe. Виртуализация KVM, x86_64, Ubuntu 24.04 LTS или Debian 12 | нагрузку дают не пользователи, а распознавание сканов, LibreOffice и сборка образа при обновлении, поэтому для 1–2 человек одновременно хватает минимума. Памяти — от 4 ГБ: swap на сервере — только страховка внутри зашифрованного диска (раздел 11), и при нехватке памяти система сильно замедляется. Образы — около 2 ГБ, кэш сборки — несколько ГБ, база и копии — меньше 1 ГБ. В OpenVZ и LXC нет зашифрованного диска |
| Доступ к модели ИИ | RouterAI или другой сервис через интернет, либо локальная модель (раздел 3.5) |
| Для HTTPS через интернет: домен и открытые порты 80 и 443 | сертификат Let's Encrypt (раздел 3.3) |

**Где.** Если анализ идёт через Codex или напрямую через OpenAI и Anthropic, сервер нужен вне России: с российских адресов они не работают. Ближе всего к России — Нидерланды и Германия: задержка около 50 мс. Не подходят хостеры, к сетям которых из России плохая связь из-за ограничений РКН (на 2026-10-20): Hetzner, OVH, DigitalOcean, Vultr, Linode, Scaleway, Contabo. Если анализ только через RouterAI, подойдёт и сервер в России.

Все команды ниже выполняются в папке с кодом (там, где лежит `docker-compose.yml`).

## 2. Первая установка

На арендованном сервере сначала включите файрвол (раздел 12), ограничьте агента хостера и смените пароль root (раздел 13), создайте зашифрованный диск (раздел 11), затем ставьте систему в `/srv/contract-review/app`: тогда код, `.env` и данные с первого дня лежат на нём.

1. Получите код:

   ```bash
   git clone <адрес репозитория> contract-review
   ```

2. Создайте `.env` со случайными секретами. Скрипт не выводит пароли в консоль:

   ```bash
   python deploy/scripts/init_env.py
   ```

3. Откройте `.env` и проверьте `PUBLIC_URL` — адрес, по которому пользователи будут открывать систему. Для работы на этой же машине оставьте `http://localhost:8080`. Остальные варианты — в разделе 3. Если анализ будет идти через Codex по подписке ChatGPT, задайте `INSTALL_CODEX=true`.
4. Соберите и запустите систему. Первая сборка занимает 10–20 минут:

   ```bash
   docker compose up -d --build
   ```

5. Убедитесь, что все контейнеры работают: у `app` и `db` должно быть `healthy`.

   ```bash
   docker compose ps
   ```

6. Откройте `PUBLIC_URL` и войдите администратором. Логин — `INITIAL_ADMIN_LOGIN` (по умолчанию `admin`), пароль — `INITIAL_ADMIN_PASSWORD` из `.env`.
7. Сразу смените пароль: «Администрирование» → «Пользователи» → «Пароль». Затем удалите значение `INITIAL_ADMIN_PASSWORD` из `.env`: администратор создаётся только при первом запуске, когда пользователей ещё нет.
8. Настройте систему в админке (README, раздел «Администрирование»): организацию с подписью и печатью, подключение ИИ, пользователей.

## 3. Варианты размещения

### 3.1. Только на этой машине

Значения по умолчанию. Приложение слушает `127.0.0.1:8080`, из сети его не видно. Адрес — http://localhost:8080.

### 3.2. Локальная сеть без HTTPS

В `.env`:

```
APP_BIND=0.0.0.0
PUBLIC_URL=http://192.168.1.10:8080
```

Пароли и договоры идут по сети открытым текстом. Так можно работать только в доверенной сети. Лучше вариант 3.4.

### 3.3. Сервер с доменом и HTTPS

Нужны домен, запись DNS на адрес сервера и открытые порты 80 и 443. Caddy сам получит и будет продлевать сертификат Let's Encrypt.

В `.env`:

```
SITE_ADDRESS=contracts.example.ru
PUBLIC_URL=https://contracts.example.ru
APP_BIND=127.0.0.1
COMPOSE_PROFILES=server
FORWARDED_ALLOW_IPS=*
```

- `COMPOSE_PROFILES=server` включает контейнер `caddy` для всех команд `docker compose`, в том числе для скриптов копирования.
- `APP_BIND=127.0.0.1` оставляет приложение доступным только через Caddy и с самой машины.
- `FORWARDED_ALLOW_IPS=*` разрешает приложению брать адрес пользователя из заголовка `X-Forwarded-For`, который ставит Caddy. Без этого ограничение попыток входа считало бы всех пользователей одним адресом. Задавайте `*` только вместе с `APP_BIND=127.0.0.1`: иначе адрес смог бы подделать любой, кто подключается к приложению напрямую.

Запуск:

```bash
docker compose up -d --build
```

Проверка: страница открывается по https, в ответе есть заголовки безопасности.

```bash
curl -sI https://contracts.example.ru/
```

В ответе должны быть `strict-transport-security`, `content-security-policy`, `x-frame-options: DENY`, и не должно быть заголовка `server`. Ответ на `http://` — перенаправление на https — Caddy отдаёт со своим заголовком `Server: Caddy`: это нормально.

### 3.4. Локальная сеть с HTTPS без домена

В `.env` — как в 3.3, но адрес — IP сервера. В `SITE_ADDRESS` он пишется без `https://`: Caddy и так включает HTTPS, а это значение ещё и выбирает сертификат для браузеров, которые открывают сайт по IP и не передают имя сервера:

```
SITE_ADDRESS=192.168.1.10
PUBLIC_URL=https://192.168.1.10
```

Сертификат выпустит внутренний центр сертификации Caddy. Пока его корневой сертификат не добавлен в доверенные на компьютерах пользователей, браузер показывает предупреждение. Корневой сертификат можно забрать так:

```bash
docker compose cp caddy:/data/caddy/pki/authorities/local/root.crt ./caddy-root.crt
```

Его устанавливают на компьютерах пользователей в хранилище «Доверенные корневые центры сертификации».

Проверять HTTPS с Windows лучше браузером или PowerShell (`Invoke-WebRequest`). Встроенный в Windows `curl` с сертификатом внутреннего центра Caddy обрывает соединение даже с `-k` — это особенность его TLS-библиотеки, а не сервера.

### 3.5. Без доступа в интернет

Модель ставится на ту же машину или в локальной сети: Ollama или vLLM, подключение «Ollama» в разделе «Подключения ИИ». Из контейнера машина видна как `host.docker.internal`. Качество локальной модели нужно проверить отдельно на своих договорах (`python -m app.cli evaluate`).

## 4. Обновление

1. Сделайте резервную копию (раздел 5).
2. Получите новую версию кода:

   ```bash
   git pull
   ```

3. Пересоберите и перезапустите систему:

   ```bash
   docker compose up -d --build
   ```

   Изменения базы применяются сами при запуске `app` (миграции Alembic).
4. Проверьте `docker compose ps` и журнал `app` (раздел 7). Если что-то пошло не так — вернитесь на прежнюю версию кода (`git checkout <прежний коммит>`) и восстановите копию (раздел 6).

Образы PostgreSQL и Caddy обновляются командой `docker compose pull` перед `up -d --build`. PostgreSQL обновляется только в пределах версии 17: переход на 18 требует отдельной миграции данных.

## 5. Резервные копии

По умолчанию — копия каждую ночь и неделя хранения на том же сервере.

**Что в копии.** Пользователи, версии промпта, подключения ИИ с зашифрованными ключами, данные организации с подписью и печатью, шаблон протокола, настройки и журнал.

**Чего в копии нет:**
- проверок, договоров и результатов анализа: они хранятся только до конца срока жизни проверки;
- сессий: после восстановления все входят заново;
- файла `.env`. Без `ENCRYPTION_KEY` из него ключи подключений ИИ из копии не расшифровать, поэтому `.env` хранится отдельно, в надёжном месте;
- входа в Codex: после восстановления администратор входит заново.

**Сделать копию** — в папку `backups/` (в git она не попадает):

```bash
python deploy/scripts/backup.py
```

Оставить 7 последних копий:

```bash
python deploy/scripts/backup.py --keep 7
```

В другую папку — `--out /mnt/backup/contract-review`.

`--dry-run` только показывает команды. Копия — дамп PostgreSQL в формате custom (`contract-review-ГГГГ-ММ-ДД_ЧЧММСС.dump`).

**Шифрование**. На сервере копии шифруются открытым ключом age, а закрытый хранится у владельца:

1. Создайте пару ключей на компьютере владельца, а не на сервере: закрытый ключ не должен появляться даже в памяти сервера, от которого он защищает копии. Нужна команда `age` (раздел 1); файл она пишет сама, поэтому команда одна для cmd, PowerShell и bash:

   ```bash
   age-keygen -o contract-review-backup.key
   ```

   Открытый ключ age печатает в консоль (`Public key: age1…`), он же — в строке `# public key: age1…` файла.
2. Впишите открытый ключ в `.env` на сервере: `BACKUP_AGE_RECIPIENT=age1…`.
3. На машине, где запускается `backup.py`, нужна команда `age` (раздел 1).

После этого копии называются `contract-review-ГГГГ-ММ-ДД_ЧЧММСС.dump.age`. Дамп шифруется в памяти: открытой копии на диске не бывает. Файл копии читает только владелец (права 600). Без `BACKUP_AGE_RECIPIENT` копия не шифруется, и скрипт об этом предупреждает. `--keep 7` считает зашифрованные и обычные копии вместе.

**Каждую ночь в Linux** (cron, `crontab -e`). Путь — папка с кодом, на сервере с зашифрованным диском — `/srv/contract-review/app` (раздел 11). Пока диск закрыт, копия не делается, и в журнале будет ошибка `cd`:

```
0 3 * * * cd /srv/contract-review/app && /usr/bin/python3 deploy/scripts/backup.py --keep 7 >> /var/log/contract-review-backup.log 2>&1
```

Время — по часам сервера: у арендованного сервера это обычно UTC, и 03:00 UTC — 06:00 по Москве. В файле `/etc/cron.d/…` между временем и командой нужно ещё имя пользователя (`0 3 * * * root cd …`), иначе cron строку не выполнит. Если настроены сигналы о работе сервера (раздел 14), ночную копию запускает `contract-review-monitor`, он же сообщает её итог.

**Каждую ночь в Windows** (Планировщик заданий; Docker Desktop должен быть запущен):

```powershell
schtasks /Create /SC DAILY /ST 03:00 /TN "contract-review backup" /TR "python C:\contract-review\deploy\scripts\backup.py --keep 7"
```

**Хранение.** В копии реквизиты, подпись и печать организации, поэтому доступ к папке с копиями — как к самим картинкам подписи и печати. Копии хранятся на том же сервере. Это защищает от ошибки и неудачного обновления, но не от поломки диска или сервера: время от времени уносите одну копию на другой носитель, например `scp root@<сервер>:/srv/contract-review/app/backups/contract-review-….dump.age .`. Зашифрованную копию без закрытого ключа не прочитать, поэтому храните её отдельно от `contract-review-backup.key`. Раз в квартал копию стоит восстановить на другой машине (раздел 6): копия, которую ни разу не восстанавливали, может не сработать, когда понадобится.

## 6. Восстановление и перенос на другую машину

Перенос — это восстановление копии на новой установке.

1. На старой машине сделайте копию (раздел 5).
2. Перенесите на новую машину файл копии и `.env`. Тот же `.env` нужен из-за `ENCRYPTION_KEY` (ключи ИИ) и `POSTGRES_PASSWORD`. Если адрес системы на новой машине другой, поправьте `PUBLIC_URL` и `SITE_ADDRESS`.
3. На новой машине установите систему по разделу 2, но вместо `init_env.py` положите перенесённый `.env`. Запустите `docker compose up -d --build`.
4. Восстановите копию:

   ```bash
   python deploy/scripts/restore.py backups/contract-review-2026-10-17_030000.dump
   ```

   Зашифрованную копию (`.dump.age`) расшифровывает закрытый ключ владельца. Он передаётся со стандартного ввода и на сервере не сохраняется:

   ```bash
   ssh root@<сервер> "cd /srv/contract-review/app && python3 deploy/scripts/restore.py backups/contract-review-2026-10-21_030000.dump.age --identity - --yes" < contract-review-backup.key
   ```

   В PowerShell ключ передаётся так же, как при открытии диска (раздел 11): `Get-Content contract-review-backup.key | ssh root@<сервер> "…"`.

   Копия расшифровывается в памяти до остановки системы: без ключа или с чужим ключом ничего не меняется. Ключ можно дать и файлом — `--identity <путь>`. Файл ключа, пересохранённый в Блокноте (с меткой BOM) или записанный PowerShell в UTF-16, тоже подойдёт: `restore.py` очищает его сам.

   Скрипт спросит подтверждение (для запуска без вопроса — `--yes`) и сделает:
   - копию текущей базы — на случай, если восстановили не тот файл;
   - остановку `app` и `worker`;
   - очистку базы и загрузку копии;
   - запуск системы: `app` применит миграции, если копия сделана старой версией.
5. Войдите и проверьте:
   - пользователи на месте и могут войти;
   - в «Организации» есть реквизиты, подпись и печать;
   - «Подключения ИИ» → «Проверить связь» проходит. Если ключ не расшифровывается, значит, `ENCRYPTION_KEY` не тот: введите ключ заново;
   - «Промпт», «Шаблон протокола» и «Журнал» — как на старой машине.
6. Если пользовались Codex, войдите в него заново («Подключения ИИ» → «Войти по коду»).

Проверки договоров не переносятся: они временные. Файлы проверок, которые были на машине до восстановления, worker стирает сам: папка без записи в базе удаляется через час, очистка идёт раз в 10 минут.

Восстановление небольшой базы занимает около минуты. Всё это время система недоступна.

Порядок раздела проверен: копия с одной установки восстановлена на чистой, всё совпало, ключ ИИ расшифровался.

Если восстановление прервалось с ошибкой после очистки базы, запустите его ещё раз с той же копией. Перед очисткой скрипт всегда делает копию текущего состояния — её тоже можно восстановить.

**Только настройки, без пользователей и журнала.** Для этого нужен не дамп, а файл настроек из админки: «Настройки и перенос» → «Выгрузить настройки», на новой машине — «Загрузить настройки». Ключи API после этого вводятся заново.

## 7. Журналы и диагностика

Журнал приложения и worker:

```bash
docker compose logs -f --tail 200 app worker
```

В журнале только идентификаторы проверок, события, числа и типы ошибок. Текстов договоров, ответов модели и текстов исключений там нет ([DATA_HANDLING.md](DATA_HANDLING.md#6-логи)). Подробность задаёт `LOG_LEVEL` в `.env`: `INFO` по умолчанию, `DEBUG` — для поиска неисправности.

| Что видно | Что сделать |
|---|---|
| `app` не становится `healthy` | `docker compose logs app`: чаще всего база ещё не готова или в `.env` не задан `APP_SECRET_KEY` |
| После смены `POSTGRES_PASSWORD` приложение не подключается к базе | пароль базы задаётся только при первом создании тома `pgdata`. Верните прежний пароль в `.env` или смените его в базе: `docker compose exec db psql -U contract_review -c "ALTER USER contract_review PASSWORD '…'"` |
| «PDF не собран» | LibreOffice в контейнере не справился: повторите; если ошибка повторяется — журнал `app` |
| Скан не распознаётся | журнал `worker`: в образе должен быть Tesseract с русским языком |
| «Codex не установлен» | образ собран без Codex: задайте `INSTALL_CODEX=true` в `.env` и выполните `docker compose up -d --build` |
| Вход в Codex по коду не проходит | в настройках ChatGPT не включён вход по коду устройства для Codex: раздел «Безопасность» (Security), в аккаунте компании на Business — у администратора рабочего пространства. Затем снова «Войти по коду» |
| Codex сообщает, что не может запустить команду (`bubblewrap`, `namespace`) | так и задумано: в контейнере песочница Codex не запускается, и команды агента не выполняются. Анализу договора они не нужны |
| «Слишком много неудачных попыток входа» у всех пользователей сразу | за Caddy не задан `FORWARDED_ALLOW_IPS=*` (раздел 3.3) |
| Ключ ИИ «не расшифровывается» | `ENCRYPTION_KEY` в `.env` сменился: введите ключи подключений заново |

Проверка, что приложение отвечает: `GET /api/health` возвращает `{"status": "ok"}`.

## 8. Секреты

| Переменная | Что будет, если сменить |
|---|---|
| `APP_SECRET_KEY` | все сессии станут недействительными, пользователи войдут заново |
| `ENCRYPTION_KEY` | сохранённые ключи подключений ИИ перестанут расшифровываться, их придётся ввести заново |
| `POSTGRES_PASSWORD` | на существующем томе базы действует старый пароль (раздел 7) |
| `INITIAL_ADMIN_PASSWORD` | ни на что не влияет после первого запуска: удалите его из `.env` |
| `BACKUP_AGE_RECIPIENT` | открытый ключ age, не секрет. Новым ключом шифруются следующие копии, старые по-прежнему открывает прежний закрытый ключ |

`.env` не попадает в git и в образ. Его копию храните отдельно от резервных копий базы.

Ключ зашифрованного диска (`contract-review-disk.key`) и закрытый ключ копий (`contract-review-backup.key`) на сервере не хранятся: они у владельца (разделы 5 и 11).

## 9. Проверки безопасности перед работой

- [ ] Пароль первого администратора сменён, `INITIAL_ADMIN_PASSWORD` в `.env` пустой.
- [ ] На сервер по SSH входят только по ключу. ## 10. Удаление

Остановить систему без потери данных:

```bash
docker compose down
```

Тома с базой, файлами проверок и сертификатами при этом остаются. `docker compose down -v` удаляет и их — всё, включая пользователей и настройки. Перед этим сделайте копию.

## 11. Зашифрованный диск на сервере

Копия или снимок диска у хостера, диск после вывода сервера из работы и выключенный сервер не раскрывают ни договоров, ни базы, ни `.env`. Для своей машины в офисе это не обязательно.

**От чего не защищает**:
- пока диск открыт, данные расшифровываются в памяти сервера, а память виртуальной машины хостеру доступна: хостер, который вмешивается в работающий сервер, может их прочитать;
- незашифрованную часть — ядро, cryptsetup, сам `contract-review-disk` — хостер может подменить, пока сервер выключен, и получить ключ при следующем открытии диска.

Шифрование диска защищает от чтения копий, но не от хостера, который решил добраться до данных. От этого помогает только свой сервер.

**Ключи — у владельца.** Их два, и на сервере нет ни одного:
- `contract-review-disk.key` — ключ диска, одна строка;
- `contract-review-backup.key` — закрытый ключ age для копий (раздел 5).

Храните оба в двух местах, например в менеджере паролей и на флешке. Потерянный ключ диска не восстановить: данные на сервере пропадут, останутся только копии. Потерянный ключ копий делает бесполезными все копии.

**Что на диске** (`/srv/contract-review`): каталоги Docker и containerd — база, файлы проверок, образы, временные файлы и журналы контейнеров; папка `app` — код системы, `.env` и `backups/`; `swapfile` — swap на 2 ГБ, страховка от нехватки памяти. На незашифрованной части — только система сервера и скрипт `/usr/local/sbin/contract-review-disk`.

**Создать диск** — один раз, после установки Docker и до первого запуска системы. Ключ создаётся на компьютере владельца, команда одна для cmd, PowerShell и bash (в Linux и macOS вместо `python` — `python3`):

```bash
python -c "import secrets; open('contract-review-disk.key', 'w').write(secrets.token_urlsafe(48))"
```

Скрипт берёт из файла первую строку и не обращает внимания на метку BOM, перевод строки Windows и кодировку UTF-16: файл, пересохранённый в Блокноте, тоже подойдёт.

На сервере нужны `cryptsetup` (`apt install cryptsetup`) и Docker из пакетов Docker (`docker-ce`), а не snap: у snap другие каталоги данных, и скрипт их не перенесёт. Скрипт копируется на сервер и запускается с ключом на стандартном вводе. Размер — с запасом под образы, базу, копии и swap: 30G при диске 40 ГБ, 40G при 60–80 ГБ. Хватит ли места, скрипт проверит сам:

```bash
scp deploy/server/contract-review-disk.sh root@<сервер>:/root/
ssh root@<сервер> "bash /root/contract-review-disk.sh setup 40G" < contract-review-disk.key
```

В PowerShell:

```powershell
Get-Content contract-review-disk.key | ssh root@<сервер> "bash /root/contract-review-disk.sh setup 40G"
```

Скрипт:
- сначала проверяет, хватит ли места, поместятся ли данные Docker и пуста ли `/srv/contract-review`. Если нет — отказывает и ничего не меняет;
- создаёт контейнер `/srv/contract-review.luks` (LUKS2) и открывает его в `/srv/contract-review`;
- останавливает Docker и отключает его автозапуск: дальше он стартует только после открытия диска;
- переносит на диск `/var/lib/docker` и `/var/lib/containerd`. Пустые каталоги на прежнем месте становятся неизменяемыми: Docker, запущенный без диска, не сможет туда писать;
- выключает swap на незашифрованной части (в `/etc/fstab` и через `swap.target`), kdump и сохранение дампов памяти, чтобы текст договора не попал туда через них;
- создаёт swap на 2 ГБ внутри диска: он включается после открытия диска и выключается перед закрытием. Файл диска подключается через loop-устройство с прямым вводом-выводом и сектором 4096 — без прямого ввода-вывода swap при нехватке памяти мог бы зависнуть, поэтому без него swap не включается;
- устанавливает себя как `/usr/local/sbin/contract-review-disk` и запускает Docker.

Если setup упал на середине, он возвращает всё как было: данные Docker на месте, файла диска нет, Docker включён и запущен. Сообщение называет шаг, на котором случился сбой; исправьте причину и запустите setup снова. Если вернуть данные не удалось, диск остаётся открытым, а сообщение называет, где они лежат: перенесите их обратно вручную, затем `bash /root/contract-review-disk.sh lock` и удалите `/srv/contract-review.luks`.

Затем система ставится по разделу 2 в папку `/srv/contract-review/app`: туда клонируется код, там же `.env` и `backups/`. Ночная копия — по разделу 5, с `cd /srv/contract-review/app`.

**После каждой перезагрузки сервера** система не работает, пока владелец не откроет диск. С компьютера владельца (cmd, Git Bash, Linux, macOS):

```bash
ssh root@<сервер> contract-review-disk unlock < contract-review-disk.key
```

В PowerShell нет перенаправления `<`:

```powershell
Get-Content contract-review-disk.key | ssh root@<сервер> contract-review-disk unlock
```

Скрипт открывает диск, запускает Docker и `docker compose up -d`. Через минуту система снова открывается в браузере. Хостер перезагружает сервер редко — при обслуживании или сбое, — но после этого кто-то должен открыть диск. О перезагрузке через несколько минут сообщит письмо, если настроены сигналы о работе сервера (раздел 14).

**Другие команды:** `contract-review-disk status` — открыт ли диск и работает ли Docker; `contract-review-disk lock` — остановить систему и закрыть диск, например перед передачей сервера.

**Проверить после установки:**
- `contract-review-disk status` — «Диск открыт»;
- `findmnt /var/lib/docker` — каталог подключён с `/dev/mapper/contract-review-data`;
- в `swapon --show` — только `/srv/contract-review/swapfile`, `cat /sys/kernel/kexec_crash_loaded` — `0` (kdump не загружен);
- `losetup --list --output NAME,DIO,LOG-SEC,BACK-FILE` — у `/srv/contract-review.luks` в колонке `DIO` стоит `1`, в `LOG-SEC` — `4096`. Если `DIO` — `0`, файловая система под файлом диска не поддерживает прямой ввод-вывод: swap на диске тогда выключен, система работает без него, и `contract-review-disk status` об этом пишет;
- после `reboot` сайт не открывается, `systemctl is-active docker` — `inactive`; после `contract-review-disk unlock` всё работает.

## 12. Файрвол на сервере

На арендованном сервере из интернета открыты только 22 (SSH), 80 и 443 (Caddy). На машине в офисе файрвол настраивают по правилам её сети.

ufw защищает службы самого сервера: sshd и всё, что поставлено не в Docker. Порты, которые публикует Docker, проходят мимо него. Приложение и базу закрывает сам `docker-compose.yml`: порт приложения — на `127.0.0.1` (`APP_BIND`, раздел 3.3), у базы портов нет.

**Включить** — от root, в одной SSH-сессии. SSH разрешается до `ufw enable`, иначе вход оборвётся:

```bash
systemctl unmask ufw.service
ufw allow 22/tcp
ufw allow 80/tcp
ufw allow 443/tcp
ufw --force enable
systemctl enable ufw.service
```

`systemctl unmask` нужен на серверах, где хостер выключает ufw сам: некоторые хостеры при первой загрузке делают `ufw disable` и маскируют `ufw.service`. Тогда `ufw enable` работает только до перезагрузки, а после неё правил нет. Если маски нет, команда ничего не меняет.

**Проверить:**
- `ufw status verbose` — `Status: active`, разрешены `22/tcp`, `80/tcp` и `443/tcp`, в том числе `(v6)`;
- `systemctl is-enabled ufw.service` — `enabled`;
- новое подключение по SSH проходит — до того, как закрыть текущее; сайт открывается;
- после `reboot` и `contract-review-disk unlock` — снова `ufw status` и сайт. ufw запускается при загрузке, Docker — после `unlock` и ставит свои правила впереди правил ufw.

Если после включения вход по SSH пропал, войдите через веб-консоль в панели хостера и выполните `ufw disable`.

## 13. Агент хостера и пароль root

Хостер обычно ставит в сервер qemu-guest-agent. Через него панель и гипервизор выполняют команды от root и читают файлы, а пока диск открыт — и данные. Агента оставляют, но запрещают ему опасное.

**Ограничить агента.** Создайте `/etc/qemu/qemu-ga.conf`:

```
[general]
block-rpcs=guest-exec,guest-exec-status,guest-file-open,guest-file-close,guest-file-read,guest-file-write,guest-file-seek,guest-file-flush,guest-set-user-password,guest-ssh-get-authorized-keys,guest-ssh-add-authorized-keys,guest-ssh-remove-authorized-keys,guest-suspend-disk,guest-suspend-ram,guest-suspend-hybrid
```

Затем выполните `systemctl restart qemu-guest-agent`. Проверить: `qemu-ga --dump-conf` показывает строку `block-rpcs`, а `systemctl is-active qemu-guest-agent` — `active`. В старых версиях qemu-ga ключ называется `blacklist`; какой нужен, видно в `qemu-ga --help`. Сброс пароля из панели хостера после этого не работает — так и задумано.

**Пароль root.** Замените пароль, выданный хостером, своим. Он нужен для веб-консоли хостера — запасного входа, когда SSH недоступен. По SSH пароль не принимается (раздел 9). Пароль создаётся на компьютере владельца и хранится рядом с ключами. Команда одна для cmd, PowerShell и bash; в Linux и macOS вместо `python` — `python3`:

```bash
python -c "import secrets; a = 'abcdefghjkmnpqrstuvwxyz23456789'; open('contract-review-root-password.txt', 'w').write('-'.join(''.join(secrets.choice(a) for _ in range(6)) for _ in range(4)))"
```

Задайте его на сервере. Пароль идёт со стандартного ввода, поэтому его нет ни в истории команд, ни в списке процессов:

```bash
ssh root@<сервер> "head -n 1 | tr -d '\r' | grep -x '[a-z0-9-]\{20,\}' | sed 's/^/root:/' | chpasswd" < contract-review-root-password.txt
```

В PowerShell:

```powershell
Get-Content contract-review-root-password.txt | ssh root@<сервер> "head -n 1 | tr -d '\r' | grep -x '[a-z0-9-]\{20,\}' | sed 's/^/root:/' | chpasswd"
```

Команда берёт из файла только первую строку. Если она не похожа на пароль из команды выше — меньше 20 знаков или есть знаки, кроме строчных латинских букв, цифр и дефиса, — пароль не меняется. Проверить — войти в веб-консоль хостера с новым паролем.

**Аккаунт в панели хостера** — с подтверждением входа, если панель это умеет: кто войдёт в панель, тот управляет сервером.

## 14. Сигналы о работе сервера

Сервер сам сообщает в Healthchecks.io, что сайт работает и ночная копия сделана. Если сигнала нет или пришёл сбой, Healthchecks.io пишет владельцу на почту. Так видно, что сервер перезагрузился и ждёт `contract-review-disk unlock`, что сайт не отвечает или что копия не сделана. Договоров и данных организации в сигналах нет.

**В Healthchecks.io** создайте две проверки. Аккаунт заводит владелец, уведомления — на его почту.
- `contract-review-site` — тип Simple, Period 5 minutes, Grace 10 minutes.
- `contract-review-backup` — тип Cron, `0 3 * * *`, часовой пояс как на сервере (`timedatectl`, обычно UTC), Grace 2 hours.

У каждой проверки есть адрес для сигналов вида `https://hc-ping.com/…`. По нему можно прислать ложное «работает», поэтому храните его как пароль.

**На сервере** — после разделов 5 и 11:

```bash
scp deploy/server/contract-review-monitor.sh root@<сервер>:/root/
ssh root@<сервер> bash /root/contract-review-monitor.sh install
```

Первый запуск создаёт `/etc/contract-review-monitor.conf` с правами 600 и останавливается. Впишите в файл адреса, например командой `nano /etc/contract-review-monitor.conf` на сервере:

```
SITE_URL=https://<адрес сервера>/api/health
SITE_PING=https://hc-ping.com/<адрес проверки contract-review-site>
BACKUP_PING=https://hc-ping.com/<адрес проверки contract-review-backup>
```

`SITE_URL` — тот адрес, по которому сайт открывают пользователи. Затем снова запустите `install`. Он:
- ставит скрипт в `/usr/local/sbin/contract-review-monitor`, на незашифрованную часть диска: скрипт работает и при закрытом диске;
- включает таймер `contract-review-monitor.timer` — проверку сайта раз в 5 минут, первую — через 3 минуты после загрузки;
- заменяет строку ночной копии в `/etc/cron.d/contract-review-backup`: копию теперь запускает `contract-review-monitor backup` и сообщает её итог, журнал — прежний `/var/log/contract-review-backup.log`;
- отправляет первый сигнал проверки сайта.

**Проверить:**
- в Healthchecks.io проверка `contract-review-site` стала зелёной сразу, `contract-review-backup` — после первой ночи;
- `contract-review-monitor test` — на почту приходит письмо о сбое, а через 5 минут — о том, что всё снова работает;
- `systemctl list-timers contract-review-monitor.timer` показывает таймер.

**Что значат письма:**
- `contract-review-site` упала с текстом «Диск закрыт…» — сервер перезагрузился: откройте диск (раздел 11);
- `contract-review-site` упала без текста — сервер выключен, у него нет сети или сайт не отвечает дольше 10 минут: `contract-review-disk status` и журналы (раздел 7);
- `contract-review-backup` упала — копия не сделана: причина — в письме и в `/var/log/contract-review-backup.log`.

Перед работами, когда сайт будет недоступен, например перед `contract-review-disk lock`, поставьте обе проверки в Healthchecks.io на паузу.
